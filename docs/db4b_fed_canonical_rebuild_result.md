# DB-4B.1 — FED Canonical Rebuild — HALTED (no changes applied)

**Status: STOPPED before modifying any code/seed/images, per the task's hard-safety rule**
("If the migration cannot be made safely, STOP and report instead of half-applying" /
"Do not force-map FED_CONFLICT entries").

## Why it was halted

DB-4B.1 has two coupled parts:
1. **Catalog rebuild** to the ~515 FED `SUPPORTED_STRENGTH` set — this part is clean and deterministic
   (regenerate directly from `free-exercise-db`; no dependency on the rename map).
2. **Name migration** of the **default templates** *and* **live user Plan rows** to FED canonical names —
   this **requires** a trustworthy `oldName -> fedCanonicalName` map. The task mandates using
   `docs/db4a_plan_name_migration.csv`.

On reading that CSV, its `FED_RENAME` column contains **multiple unsafe auto-matches**. The DB-4A mapping
was generated by a token-overlap (jaccard) matcher whose conflict-keyword detection was incomplete, so it
mapped several exercises to the *wrong* FED variant. Applying this map to **live user Plan rows** would
**corrupt exercise names** and attach wrong canonical identities.

### Evidence (from `db4a_plan_name_migration.csv`, 92 rows)

**FED-name collisions — distinct AURON exercises collapsing to one FED name (7 → 3):**
- `Dumbbell Flat Bench Press` **and** `Dumbbell Incline Bench Press` → "Dumbbell Bench Press"
- `Push-Up`, `Diamond Push-Up`, `Pike Push-Up` → "Pushups"
- `Forearm Plank` **and** `Side Plank` → "Plank"

**Defining variant-keyword mismatches (14) — different exercise/setup:**
| old (AURON) | mapped (FED) | problem |
|---|---|---|
| Barbell Flat Bench Press | Barbell **Guillotine** Bench Press | neck-level variant ≠ flat bench |
| Dumbbell **Incline** Bench Press | Dumbbell Bench Press | incline → flat |
| Wide-Grip Pull-Up | Wide-Grip **Rear** Pull-Up | front ≠ behind-neck |
| Close-Grip Lat Pulldown | Close-Grip **Front** Lat Pulldown | (ok-ish, but flagged) |
| T-Bar Row | **Lying** T-Bar Row | standing ≠ chest-supported lying |
| **Overhead** Dumbbell Triceps Ext. | **Decline** Dumbbell Triceps Ext. | overhead ≠ decline |
| **Diamond** Push-Up | Pushups | distinct triceps variant lost |
| Dumbbell **Goblet** Squat | Dumbbell Squat | goblet ≠ generic |
| **Seated** Dumbbell Shoulder Press | Dumbbell Shoulder Press | seated → unspecified |
| Cable Lateral Raise | Cable **Seated** Lateral Raise | standing → seated |
| Dumbbell Incline **Rear Delt** Row | Dumbbell Incline Row | rear-delt → mid-back |
| **Pike** Push-Up | Pushups | shoulder movement → chest pushup |
| **Side** Plank | Plank | side ≠ front |
| **Lying** Reverse Crunch | Reverse Crunch | (minor, flagged) |

≥14 of the 92 are clearly wrong, plus the 3 collisions. The `FED_EXACT` rows and *many* `FED_RENAME` rows
(e.g. Seated Cable Row→"Seated Cable Rows", Arnold Press→"Arnold Dumbbell Press", Lying Leg Curl→"Lying
Leg Curls", Machine Shoulder Press→"Machine Shoulder (Military) Press", Concentration Curl→"Concentration
Curls") are correct — but the map as a whole is **not safe to apply blindly to user data**.

## Why "catalog-only, skip the plan migration" is also not acceptable

Rebuilding the catalog to FED canonical **without** migrating active Plan names would leave existing user
Plan exercises on old AURON names that no longer exist in the catalog → `findByName` returns null →
Engine V3.6B **falls back to name inference** for those exercises. That is exactly the regression DB-4B.1
is meant to prevent, and it is a **half-migration** (explicitly forbidden). So neither the full apply
(corrupts data) nor the partial apply (half-migration) is safe with the current map.

## What was NOT changed

- No `CatalogSeed`, no catalog JSON, no Room schema/version, no `SeedData`, no engine, no UI.
- No images copied/deleted; no `imageRefs` changed; no Plan/History/Draft rows touched.
- Only **backups** were created and files **read**.

## Recommended path (corrected, two-step)

**DB-4A.1 — Regenerate a verified rename map first.** Rebuild `db4a_plan_name_migration.csv` with:
- a complete conflict-keyword list (add: guillotine, lying, seated, standing, decline, rear, front, wide,
  side, diamond, pike, goblet, sissy, pistol, kettlebell, single/one-arm, sumo, deficit, preacher, …) so
  variant mismatches are demoted to `FED_CONFLICT`, **not** renamed;
- a rule that **rejects collisions** (two AURON exercises must never map to the same FED name);
- a requirement that each FED target **exists in the final 515 catalog**;
- a short human-review pass (the same discipline as DB-3D.3, which found 18 safe of 79).
Expected safe rename set ≈ the `FED_EXACT` rows + the genuinely-clean `FED_RENAME` rows (~50–60, not 92).

**Then DB-4B.1 (re-run) can safely:** rebuild the 515 FED catalog, re-key images, rename templates +
active Plan rows using the *verified* map only, leave conflicts/no-FED as custom (engine name-inference),
and preserve History.
